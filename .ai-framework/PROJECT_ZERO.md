# PROJECT_ZERO — подготовка проекта

Режим PROJECT_ZERO предшествует полноценной разработке нового проекта. Для существующего проекта это аудит пробелов, а не требование перепроектировать продукт. INIT устанавливает и настраивает ядро; PROJECT_ZERO согласует продукт и готовность. Не начинать DEVELOP, пока не пройдены оба этапа. AUDIT, PLAN, DOCS, безопасные проверки и явно разрешённая разведка доступны раньше.

## 1. Интервью и возобновление

Сначала изучи доступные реальные документы, код (если есть), ограничения пользователя. Не спрашивай повторно уже известное. Задавай небольшие блоки по 1–3 вопроса, сначала самые важные. Объясняй варианты простыми словами, рекомендуй разумный вариант, указывай компромиссы. Не требуй от владельца знания технологий. Разрешён ответ «реши сам», но только в пределах согласованных полномочий; решение и основания всё равно фиксируй. Не выдавай рекомендацию за согласование.

Порядок адаптивный; этапы можно пройти вместе, но нельзя молча пропустить обязательные темы:

| Тема (ID) | Вопросы и результат | Канонический источник (пример) |
|---|---|---|
| purpose | Что создаём, для кого, какую проблему решаем, измеримый успех? | README / VISION |
| scope | MVP, обязательное, позже, явно вне границ, основные сценарии и критерии | REQUIREMENTS / README |
| prototype | Экраны/сценарии, макеты или технический эксперимент; что согласовано? Для проекта без UI обоснуй неприменимость | DESIGN_SYSTEM / ARCHITECTURE |
| architecture | Платформы, ограничения, варианты стека, выбор с аргументами, данные и интерфейсы | ARCHITECTURE / DECISIONS |
| autonomy | Самостоятельные решения, уведомление, явные разрешения, ограничения инструментов | AI_WORKFLOW / AGENTS |
| regression | Сохранение поведения, существующие данные, baseline-тесты; для нового проекта — как закрепить критерии | TEST_MATRIX / DEFINITION_OF_DONE |
| environment | Воспроизводимая настройка, сборка, тесты; план при отсутствии среды | ENVIRONMENT / README |
| changes | Как согласовывать изменения требований, вести историю и пересматривать roadmap | DECISIONS / AI_WORKFLOW |
| task_readiness | Критерии готовности задач и первоначальный порядок реализации | ROADMAP / AI_WORKFLOW |
| uncertainty | Предположения, открытые вопросы, влияние и способ проверки | DECISIONS / HANDOFF |
| complexity | Бюджет сложности, зависимости, минимальное решение, сроки/ресурсы если заданы | ARCHITECTURE / DECISIONS |
| risks | Возможные отказы, безопасность, данные, восстановление, план отката | ARCHITECTURE / SECURITY / RECOVERY |

Для маленького проекта объединяй темы в несколько коротких разделов; не требуй 12 отдельных интервью. В черновике допустимы неизвестные команды и отсутствие кода; опиши план проверок вместо фиктивных тестов. Не создавать документы по числу тем: записывать содержательные ответы в уже выбранные источники из карты project.json. `.ai-framework/project-zero.json` хранит только состояние интервью, ссылки, открытые блокеры и запись согласования, а не второе ТЗ. Если источник ещё не определён — оставь тему open. После каждого блока обновляй состояние, следующий вопрос и HANDOFF (без дублирования ответов). Новый чат читает состояние, соответствующие источники и задаёт следующий нерешённый вопрос. Не сохраняй секреты, персональные данные без необходимости, сырые логи.

## 2. Полномочия и ограничения

По умолчанию самостоятельно: анализ, предложения, документация в пределах задания, безопасные локальные проверки после обзора команд. Уведомлять о компромиссах, новых зависимостях, изменении оценок/рисков. Явное разрешение: разрушительные действия, миграции с риском потери данных, публикация, расходы, секреты, расширение доступа, существенная смена согласованной концепции или архитектуры. Более строгие правила проекта/среды выше. Делегирование технического выбора не является разрешением на опасные действия. Укажи конкретные границы в источнике autonomy.

## 3. Готовность и согласование

- `draft` — интервью; `review` — сформирован план и ожидается решение; `approved` — владелец явно подтвердил конкретный план. Не записывай одобрение за пользователя. Если он исправляет план, вернись к review и повторно согласуй.
- Тема `resolved` имеет ссылку на реальный локальный файл (при необходимости раздел) или внешний источник с пояснением; `not_applicable` допускается для prototype с причиной. Остальные темы обязательны; неизвестное описывай как open или явный блокер. Неблокирующие неизвестные допустимы, если есть план проверки, зафиксированный в каноническом источнике. У блокера есть ID, описание и следующий шаг; открытый блокер не позволяет начать DEVELOP.
- Первоначальный ROADMAP: этапы, целевые релизы, небольшие задачи с ID, приоритетами, зависимостями, критериями и проверками. Только согласованный scope; не помечать задачи done без доказательств. Для существующего проекта сохранить источник, задачи и историю, добавить только согласованные пробелы. Нативная карта не должна быть пустой при согласовании нового проекта. Для existing/external необходима ручная проверка по ROADMAP_STANDARD.
- Definition of Ready для задачи: согласованный scope, понятный результат и критерии приёмки, зависимости выполнены, известные проверки, доступное окружение, разрешения, риски и способ отката при необходимости; нет блокеров, назначение согласовано. Это дополняет ROADMAP_STANDARD, а не заменяет Definition of Done.
- Перед одобрением покажи владельцу краткое резюме: цель, MVP и исключения, архитектура, полномочия, существенные риски, первый этап, вопросы. Выполни `python .ai-framework/tools/verify.py --proposal` (конфигурация active, все темы закрыты, нет открытых блокеров, ROADMAP нового проекта заполнен), зафиксируй полученный отпечаток в запросе на подтверждение или свяжи ответ с именно этой редакцией. После явного подтверждения запиши `approval` (approved_by, confirmed_at ISO 8601 с зоной, evidence — ссылка/описание фактического ответа, fingerprint). Только тогда status=approved. Перед согласованием зафиксируй конкретное резюме утверждаемого плана в DECISIONS или другом выбранном источнике (в Git — ссылка на ревизию; без Git — датированная запись). Сошлись на него в evidence. Отпечаток учитывает поля подготовки и ссылки, но не содержимое меняющихся рабочих документов; при существенных изменениях агент обязан вернуть status=review и очистить approval. Не выдавать проверку JSON за проверку подлинности разрешения.
- Запусти `python .ai-framework/tools/verify.py --ready` перед DEVELOP, REFACTOR, UX с изменением кода, RELEASE и продолжением таких работ через RESUME. Это проверка структуры и записи согласования, не предоставление прав. Если Python недоступен — ручная проверка тех же условий, явно отметить ограничение. `verify.py --strict` по-прежнему проверяет только настройку проекта, а `--run` может использоваться для безопасных диагностических проверок до согласования. Не считать это обходом gate.

## 4. Новый и существующий проект

`project_kind`: new или existing; до анализа unknown. Для existing сначала аудит и baseline без изменения поведения. Существующая документация переиспользуется; нельзя автоматически заявлять, что старый проект согласован. Если полноценная реализация уже идёт, отдели обследование/устранение аварии в пределах явного разрешения от новых работ, не блокируй диагностику. Разведочный прототип возможен до approval только при отдельно согласованных ограничениях (scope, время, изолированные файлы/ветка, без production и чувствительных данных), его результат не означает готовность к полноценной разработке.

## 5. После согласования

Включи обычный цикл работы через AGENTS и ROADMAP. При существенной смене требований/платформы, полномочий, рисков или MVP повтори затронутые темы и согласование, не пересоздавай проект. Обычное продвижение задач не требует повторного интервью. PROJECT_ZERO — рабочий протокол, не автономный агент; он не запускает интервью сам и не может заставить сторонний ИИ подчиняться.
