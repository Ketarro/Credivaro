## Три предлагаемых решения (не согласованы)
1. Платёжный журнал. Фактические платежи положительной суммы в валюте обязательства, точные minor units, UUID, operationId для повторов, дата в банковской зоне, примечание. Распределение principal/interest/fee и явная нераспределённая часть; сумма частей равна платежу, переполнение/отрицательные части/чужая валюта отклоняются, отсутствие распределения не равно нулю. Снимок банка не меняется автоматически: оценка principal только при известном исходном principal и известных применимых операциях после снимка; если дата/порядок/распределение не ясны, показать неполноту, не выдумывать остаток. Переплата отдельно, не обрезать долг до нуля. Исправление/отмена атомарной цепочкой reversal/replacement, без перезаписи исходных фактов. Архивация предпочтительна; явное подтверждённое полное удаление существующего обязательства остаётся отдельной командой с предупреждением об удалении истории, не заменяет отмену платежа. Минимальный срез: модель/репозиторий и migration (R03.06/R04.01), далее редактор, распределение, исправления и сверка R04.02–05; реальные связи с календарём R04.06 при наличии сущностей событий R05, не создавать фиктивные event ID. R04.01 целиком не закрывать, пока все его критерии не выполнены; зависимость R04.06/R05 сверить в конечном плане. Не менять 68 задач. В MVP не вводить автоматическую конвертацию: другая валюта требует ручной сверки, явный FX только отдельным согласованным решением.
2. Миграция. Предпочесть минимально добавочную v1→v2 с новыми таблицами и индексами, не переписывая v1 обязательства/terms/snapshots, не менять DB name, Keystore alias, envelope, SQLCipher/KDF или подпись. Явная Room Migration, экспорт v1/v2, без destructive fallback. Реальная синтетическая зашифрованная база, созданная v1 кодом с историей всех типов, нулём/unknown и несколькими валютами; проверки успешного upgrade с тем же ключом, идентичность доменных записей и ревизий, FK/schema/integrity, повторное открытие, атомарный rollback при внедрённой ошибке, повторная попытка, неправильный ключ/отсутствующий envelope, недостаток места и аварийный перезапуск. CI API26/36 + signed install matrix и физический synthetic upgrade после review и отдельного разрешения. Не считать downgrade старого APK безопасным после успешной v2 миграции: rollback при ошибке до commit, после commit — проверенное восстановление из специально подготовленной согласованной копии либо исправление вперёд; переносимый backup не обещан. Не выполнять миграцию реальных пользовательских данных. Независимый review схемы, транзакций, ключей и плана отказа обязателен до распределения миграционной сборки. Реальное выполнение рискованных действий требует отдельной санкции.
3. Политика безопасности. До итоговой приёмки только синтетические данные; сохранение fail-closed при повреждении/потере ключа, без автоудаления, переустановки или подмены ключа. Отсутствие переносимого backup означает риск безвозвратной потери данных при утрате устройства/ключа; показать предупреждение и отдельно согласовать любые процедуры восстановления/удаления. Не внедрять небезопасные временные копии, не обещать восстановление без проверенного механизма. Опциональная системная аутентификация, приватные уведомления, backup/transfer exclusions, отсутствие финансовых логов, threat-model и проверки ARM/16KiB/зависимостей остаются обязательными согласно R08/R03.08/R09.05. Полный переносимый backup/export/import после alpha по согласованному scope. Самопроверки дополнить synthetic migration/payment cases после допуска, не трогать рабочую базу; запись экрана не доказывает отсутствие утечек.
