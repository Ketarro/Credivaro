# ROADMAP_STANDARD — единый стандарт дорожной карты

## Источник истины
Одна дорожная карта на проект. Используй источник `sources.roadmap` из project.json. Для нового проекта — ROADMAP.md по шаблону. Для существующего — сохрани ID, историю, статусы и ссылки, согласуй переход; если уже есть GitHub Issues/Projects или иной трекер, применяй правила в нём, не создавай вторую карту. `roadmap_format`: `native` (таблица стандарта), `existing` (иной локальный формат), `external` (внешний трекер). Для последних двух требуется `roadmap_policy_note` с соответствием полей и способом проверки; локальный валидатор не проверяет содержание этих форматов.

## Поля и порядок
Одна строка — одна задача; ID постоянный (например, CORE-001), не переиспользовать. Этап и целевой релиз — отдельные поля (допустимо `TBD` для planned). P0 — критично, P1 — высокий, P2 — обычный, P3 — низкий. Зависимости — ID через запятую либо `-`; все обязательные зависимости должны быть done до старта. Владелец — агент/человек и при возможности ссылка на ветку или PR. В таблице не используй вертикальные черты внутри значений, многострочные значения вынеси в реальные документы и укажи ссылки. Не записывай секреты.

Статусы (те же, что в EXECUTION_CONTRACT):
- `planned`: запланировано, не начато; критерии и проверки обязательны для готовности к выбору. Не утверждённые задачи оставляй с `TBD` в критериях или проверках.
- `in_progress`: задача взята владельцем, зависимости закрыты, scope и проверки согласованы.
- `review`: реализация предъявлена, владелец и ссылка на проверяемый результат есть; ожидаются проверки/приёмка.
- `blocked`: укажи конкретный блокер и следующий шаг для снятия; не занимайся им без полномочий.
- `done`: все критерии и обязательные проверки пройдены, получены необходимые согласования; зафиксированы доказательства (коммит/PR, конкретный отчёт/лог, команда и результат, ручная приёмка когда нужна). Ссылка сама по себе не доказывает успех. Публикация обязательна только если входит в критерии.
- `cancelled`: причина обязательна; зависимые задачи необходимо перепланировать, не считать зависимость закрытой.

Обычный переход: planned → in_progress → review → done; из активного состояния можно перейти в blocked; после снятия блокера вернуть в planned или in_progress при выполнении условий. Из review можно вернуть в in_progress. Переоткрытие done и отмена — с причиной, с проверкой зависимых задач и записью истории. Не исправляй историю задним числом. История — Git/трекер; отдельный журнал не нужен. Существенные изменения scope, приоритетов и релизов фиксируй в истории источника/DECISIONS при необходимости. Не меняй согласованные границы без необходимых полномочий.

## Выбор следующей задачи
1. Сначала проверь текущую контрольную точку и фактический Git; не начинай новую задачу вместо незавершённой назначенной.
2. Для новой задачи отфильтруй planned без владельца/блокера, с определёнными этапом и релизом, критериями и проверками (не TBD), всеми зависимостями done.
3. Сортируй P0–P3, при равенстве сохраняй порядок строк (владелец проекта устанавливает его по этапам). Не бери задачу за пределами запрошенного этапа/разрешений. Кандидат не является автоматическим назначением.
4. Перед началом перепроверь актуальность ветки/трекера, согласуй владение и отсутствие пересечений файлов. В параллельной работе используй штатное назначение/PR; локальный скрипт не блокирует гонки.
5. Обновляй статус и контрольную точку после существенных действий, при завершении сверяй roadmap, тесты, CHANGELOG (если применимо) и фактический результат. Не закрывай задачу по одному сообщению агента.

## Автоматизация
`python .ai-framework/tools/roadmap.py` — проверка структуры native и список кандидатов; `python .ai-framework/tools/verify.py --strict` также проверяет native. Валидатор проверяет ID, ссылки на задачи, циклы, поля по статусам и зависимости; не подтверждает реальные тесты, владельцев, историю переходов, содержимое доказательств или публикацию. Для existing/external явно сообщай, что проверка содержимого не выполнялась; используй штатный трекер. Не создавай фиктивные строки для прохождения проверки. Не используй количество задач как единственную метрику прогресса.

## Связь с PROJECT_ZERO
Первоначальная карта формируется из согласованного MVP; новая нативная карта должна содержать задачи до допуска к разработке. Кандидат, выданный roadmap.py, не является разрешением начать: перед реализацией проверь PROJECT_ZERO и `verify.py --ready`, Definition of Ready задачи и полномочия. Не создавать отдельную карту PROJECT_ZERO.
